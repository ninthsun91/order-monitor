> **v1.16 개정 (2026-08-02, 멀티 거래소 확장 스펙 토의 — 사용자 확정)**: **고래 유동성 거래소(Coinbase·Kraken·Bitfinex)로의 관측 확장 — 거래소별 독립 파이프라인, D1+D3+D5 한정** (§2, §3, §5.5 신설, §9.3, §10, §12, §13 M8, §14, §15 #6, §16). 배경: 대형 벽 추적의 전제("큰 가격 움직임엔 스마트머니 주체가 동반된다" — 사용자)에서 바이낸스 단독 관측은 고래 유동성의 절반만 본다. 선정 축은 현물 거래량 점유율이 **아니라 ±1% 뎁스(고래 유동성)** — 실측(2026-08-02, BTC ~$62.9k, ±1% 누적 뎁스 BTC): Binance 539 / **Kraken 489**(거래량 ~1/20인데 뎁스 91%) / **Coinbase 298** / **Bitfinex 253** / OKX 172 / Bybit 100. Kaiko 1% 뎁스 순위도 Coinbase·Kraken이 1·2위, Binance 3위 — 거래량 2위 Bybit가 뎁스 최하위로, 두 지표는 완전히 다른 축이다(OKX·Bybit는 MM 호가 위주 얇은 북이라 후순위). 골자: (1) **거래소별 독립 파이프라인 — 합산 금지**(§3 비목표 유지): 벽·체결 귀속·epoch·임계값·판정 전부 거래소 스코프, 가격축(USD/USDT)도 분리. 거래소 간 접점은 알림 venue 태깅(§9.3)과 events DB의 exchange 축(§12) 둘뿐. (2) **디텍터 스코프 = D1+D3+D5** — 벽 수명주기 전체(출현→접촉 체결 누적→진행률→확정→FILLED/PULLED 소멸)를 신규 거래소에서 동일 재현. D2·D4 제외(100ms 근접북 스냅샷 케이던스 의존 + 자체 로직 M6 튜닝 중), W 제외(명령의 거래소 인자 확장은 독립 후속). (3) **어댑터 계약**: 신규 코드는 어댑터(WS+정규화+epoch 규칙)로 한정 — 정규화 이벤트 3종을 생산하면 상태·디텍터·알림·영속화 무변경 재사용. 구독 = 절대잔량 채널 + 체결 + ticker(최우선호가), **로컬 풀북 유지 금지**(D2·D4 제외가 정확히 이 필요를 제거 — D1+D3+D5 입력은 셋 다 풀북 불필요). (4) **DB**: 단일 DB + `exchange` 컬럼(walls·intents PK 재생성, events ALTER, alerts_outbox UNIQUE 재생성 — §12). (5) **임계값 데이터 선행**: 1000 BTC는 바이낸스 스코프 값(신규 3곳 현재 최대 오더 30~60 BTC 실측) — 낮은 관측 플로어로 분포 수집 후 확정(§15 #6). 1차 대상 Coinbase(유일한 full-book 절대잔량 채널 — 이식성 최상), Kraken·Bitfinex는 후속.

> **v1.14 개정 (2026-07-23, M7 실배포 검증 후속 — 사용자 확정)**: **텔레그램 수신의 채널 게시 수용 + 명령 허용 chat 복수화** (§9.5, §10). 배경(실배포 발견 2건): ① 운영 대상이 그룹이 아닌 **채널**인데, 채널 게시물은 Bot API에서 `message`가 아닌 별도 업데이트 타입 `channel_post`로 도착 — v1.13 구현은 `message`만 읽어 채널 명령이 인증 검사 도달 전에 무기록 스킵됨(unauthorized 로그조차 없음이 진단 단서). ② 봇 DM 명령은 단일 `chat_id` 인증에 걸려 거부 — 설계 의도였으나 다중 채널/그룹/DM 확장 요구 확인. 변경: (1) 수신 대상 = `message` + `channel_post`. (1) **② 은닉 리필의 1틱 이월 보정**: 체결 이벤트와 그 감소를 반영한 스냅샷이 스트림 순서 역전으로 서로 다른 틱에 떨어지면, 감소분은 앞 틱에서 `max(0,…)` 클램프로 버려지고 체결은 뒤 틱에서 은닉 리필로 오인된다 — 오차가 양의 방향으로만 누적되어 리필 없이 그냥 먹히는 벽에서도 absorbed가 쌓이는 오발화 경로(스트림 역전은 §13 replay 필수 시나리오로 실재가 확인된 현상). 보정: 직전 틱의 "체결 없는 잔량 감소" 초과분을 다음 틱 계산에서 차감, 이월은 1틱 한정(오차 국소화 원칙 유지). (2) **epoch 시작 시 스트릭 재개시**: v1.11은 epoch 종료의 누적 리셋만 정의하고 생존 벽의 스트릭 재개를 미정의 — 스트릭 개시가 신규 레지스트리 등록에만 걸리면 재시작 복원 벽·epoch 생존 벽이 완전 소멸 후 재등록 전까지 D4 사각이 된다(장수 준임계 벽이 주 표적인데, v1.5가 D5에서 폐지한 "죽은 창"과 같은 부류). 새 epoch 시작(재시작 복원 포함) 시 활성 레지스트리 벽 전체에 새 스트릭을 개시하고 R = 그 시점 `last_qty`로 재고정한다. (3) §10 삭제 목록에 `iceberg_min_trades` 명시(`absorb_min_events`가 계승 — v1.11에서 암시만 되어 있던 것을 정리). 부수 확인: 케이스 2 폐지로 `d5.reset()`을 `d4.reset()`보다 먼저 호출해야 하던 순서 제약(2026-07-14 결정)은 근거(`above_realized_rate`의 D4 lifetime 조회)와 함께 소멸.

> **v1.11 개정 (2026-07-22, D4 재설계 스펙 토의 — 사용자 확정)**: **케이스 2(상위 구간 은닉 체결의 하위 인텐트 귀속) 폐지 + D4를 "레벨 흡수 방어" 디텍터로 재설계** (§1, §2.1, §4, §8 D4, §8 D5, §9, §10, §14, §15 #2). 원칙: **관측은 기계가, 의도 해석은 수신자가** — 공개 스트림에 주문 소유자 정보가 없어 귀속은 데이터상 불가능한데(§8 D5 판정 의미), 케이스 2는 시스템에서 유일하게 "이 리필은 저 벽 주인의 것"이라는 해석을 기계가 대신하던 곳이고 v1.6 한계 3건이 전부 그 해석에서 나왔다. 결정적 근거 실측(07-17 15:02 KST, 62.8k bid): 상위 구간 리필의 오염원이 v1.6 서술("무관한 MM 노이즈")과 달리 **1000 BTC 기준에 못 미쳤을 뿐인 독립적 매수 의도**(peak 220 BTC, ~200 BTC급 반복 리필 방어)일 수 있음 — 이를 61k 인텐트의 실행 증거로 합산하면 오귀속이고, 버리면 준임계 독립 의도가 무통지. 재설계: (1) `EXECUTION_INFERRED_ABOVE`·케이스 2 집계·`REALIZE_PCT_ABOVE` 폐지, D5는 케이스 1 전용(§15 #2 종결 — 상위 구간 범위 제한 질문 자체가 소멸, v1.6 파생 결함 ③도 영구 소멸). (2) D4는 레지스트리 추적 레벨(관측 하한 100+) 전체를 대상으로 **자기 레벨에서의 방어 행동**을 독립 감지·통지한다(구 "케이스 2의 재료" 역할 폐지, D5 미공급). 판정은 표시 크기 기준이 아니라 **리필로 입증된 흡수의 배수**: `absorbed ≥ M × 기준크기` — absorbed = ① 체결 페어링 가시 리필(`refill_added`, v1.2 산식 유지) + ② **스냅샷 틱(100ms) 단위 대조** 은닉 리필(`max(0, 틱 내 체결 − 틱 내 표시잔량 감소)` 합산 — v1.6 한계 ② 네이티브 아이스버그 사각 해소. episode 전체 뭉뚱그림 대조는 v1.2가 폐기한 경로 소실 결함의 재발이라 금지). 원시 체결 총량을 쓰지 않는 이유: 장시간 횡보 회전(다수 참여자의 소진·무관 재유입)이 배수 기준을 넘어 오발화 — 횡보는 체결이 실제로 잔량을 깎아 틱별 mismatch ≈ 0, 재유입은 체결과 페어링되지 않아 자연 배제된다. 저유동성 국면 발화는 의도된 동작(걸러내는 축은 유동성 수준이 아니라 리필 입증 여부). ## 1. 배경 및 문제 정의

Bookmap 히트맵에서 관찰되는 대형 리밋 오더(예: 특정 가격의 1k+ BTC bid)는 그 자체로는 "체결 의도의 가설"일 뿐이다. 실제로 확인하고 싶은 것은 다음 질문이다:

> **"확인된 매수 의도에 준하는 물량 체결이 실제로 이루어졌는가?"**

구체적으로 두 가지 케이스를 판별해야 한다:

- **케이스 1**: 가격이 해당 레벨까지 도달하여 그 자리에서 실제 체결이 이루어짐 (흡수, absorption)
- ~~**케이스 2**: 가격이 해당 레벨까지 도달하지 못했지만, 그 위쪽 가격대에서 아이스버그 등으로 충분한 물량을 확보함~~ → **폐지 (v1.11)**: 상위 구간 활동을 하위 인텐트에 귀속하는 해석은 공개 데이터로 성립 불가. 대신 해당 활동 자체를 D4 흡수 방어 신호로 독립 통지하고 의도 해석은 수신자 몫으로 둔다 (§8 D4)

Bookmap으로 육안 확인은 가능하나 24/7 자동 모니터링이 필요하다. Bookmap API는 원격 호출형이 아닌 **실행 중인 GUI 앱에 로드되는 인프로세스 애드온** 모델이므로, 24/7 운영 시 GUI 앱 상주라는 운영 부담이 생긴다. 반면 필요한 원천 데이터(오더북 depth, 체결)는 Binance 등 거래소 WebSocket으로 무료·무인증 제공된다.

**결정: 경로 B — Bookmap 없이 거래소 WebSocket을 직접 소비하는 헤드리스 Python 서비스로 구현한다.** Bookmap은 데스크톱에서 리서치/임계치 튜닝/육안 검증용으로만 사용한다.

## 2. 목표

1. Binance 현물 BTC/USDT 오더북과 체결을 실시간 소비하여, "매수(또는 매도) 의도가 실체결로 이어진 순간"을 자동 감지한다. **(v1.16)** 관측 대상을 고래 유동성 거래소(Coinbase·Kraken·Bitfinex의 BTC/USD 마켓)로 확장한다 — 거래소별 독립 파이프라인, D1+D3+D5 한정 (§5.5).
2. 확정 신호만 Telegram으로 발송한다 (노이즈 최소화).
3. **신뢰성 최우선**: 정밀도·속도보다 무중단·자가복구·오탐지 억제를 우선한다.

## 4. 용어

| 용어 | 정의 |
|---|---|
| 레벨(level) | 오더북의 특정 가격과 그 가격의 표시 잔량 |
| aggressor | 시장가로 체결을 일으킨 쪽. aggTrade의 `m=true`→매도 aggressor(비드 히트), `m=false`→매수 aggressor(애스크 리프트) |
| 의도(intent) | 임계 크기 이상이고 최소 지속시간을 통과한 대형 레벨. "체결을 희망하는 물량"의 후보 |
| 실현률 | 의도로 등록된 표시 크기 S 대비 해당 레벨의 실제 체결 누적량 비율 (v1.11 — 케이스 2 폐지로 케이스 1 단일 정의, §8 D5) |

| 흡수 배수 (v1.11) | D4 기준크기 R 대비 리필로 입증된 흡수량(absorbed) 비율 — 표시된 크기의 몇 배를 먹으며 버텼는가 (§8 D4) |

## 5. 데이터 소스

### 5.1 스트림 (Binance Spot WebSocket)

| 스트림 | 용도 | 주기/특성 |
|---|---|---|
| `btcusdt@depth20@100ms` | 근접 오더북 상태 | 상위 20레벨 bid/ask **완전 스냅샷**을 100ms마다 push. 시퀀스 재조정 불필요 |
| `btcusdt@aggTrade` | 체결 | 체결 발생 시 push. 가격·수량·시각·`m` 플래그(aggressor 방향) 포함 |
| `btcusdt@depth@100ms` (diff) | **대형 레벨 이벤트 탭** → 벽 레지스트리 | 변경된 레벨의 **절대 잔량**을 push (델타 아님). 가격 거리 제한 없음. full book 유지에는 사용하지 않음 (v1.1) |

**설계 결정 1 — 근접 오더북 상태는 partial snapshot(`@depth20@100ms`) 채택.**
diff 스트림으로 full book을 유지하려면 REST 스냅샷 + U/u 시퀀스 재조정 + 갭 재동기화가 필요해 로컬 북 드리프트라는 버그 클래스가 존재한다. 근접 정밀 판정(D3 흡수 등)은 상위 20레벨로 충분하므로, 매 메시지가 완전 스냅샷인 partial 스트림을 채택해 해당 버그 클래스를 원천 제거한다. 신뢰성 우선 원칙에 부합.

**설계 결정 2 (v1.1) — 원거리 대형 벽은 diff 스트림을 "이벤트 탭"으로만 소비하는 벽 레지스트리로 추적.**
실측(2026-07-11 스파이크)으로 확인된 사실: top-20 창의 실제 폭은 현재가 ±$0.2~5(호가 밀도에 따라 변동)에 불과하고, REST depth는 limit 상한 5000으로 ±$1,000 수준까지만 닿는다. 즉 61k 벽 같은 원거리 물량은 partial/REST로는 원천적으로 관측 불가하며, Bookmap/Coinglass도 diff 스트림 상시 청취로 상태를 누적하는 방식이다. Binance spot diff 이벤트는 (1) 가격 거리 제한이 없고 (2) 변경된 레벨의 **절대 잔량**을 실어 보내므로, full book 없이 "임계치 이상 레벨만 골라 절대값으로 덮어쓰는" 레지스트리가 가능하다. 이벤트를 놓쳐도 다음 이벤트가 진실을 복원하는 자가치유 구조라 드리프트 버그 클래스가 성립하지 않는다 (드리프트는 full book의 일관성 유지에서 생기는 문제). 실측: 신규 접속 4분 만에 61000 레벨 1,364.86 BTC 포착, 부하 초당 ~10 이벤트.

**diff 누락 탐지 (v1.2)**: 위 자가치유는 가격별 서술이다 — 놓친 이벤트가 tombstone(잔량 0)이면 그 가격에 다음 이벤트가 영영 없을 수 있어 유령 벽이 남는다. 따라서 diff 이벤트의 `U`/`u`(update ID 범위)로 연속성(직전 `u`+1 = 현재 `U`)을 검사하되, **누락 탐지 전용**으로만 사용한다 (full book 재구성·시퀀스 재조정에는 여전히 사용 금지 — §3, §16 기각 사유 유지). 갭 발견 시 청취 공백으로 취급한다: epoch 종료(§5.4) + 레지스트리 전체 `unconfirmed` 마킹(§12.1).

**한계 (수용)**: 청취 시작 *이전*에 설치되고 이후 한 번도 변경되지 않은 벽은 첫 변경 이벤트가 올 때까지 보이지 않는다 (Coinglass 등도 동일한 제약이며, 이들의 시야는 수개월치 누적의 결과). 대형 벽은 활발히 관리되는 물량이라 상시 가동 시 빠르게 수렴한다(실측: 61k 벽 3분 내 이벤트 발생). 청취 공백(재시작·재연결) 동안의 변경은 놓칠 수 있으며, 이는 §12의 unconfirmed 플래그로 처리한다.

- 재연결 직후의 판정 재개는 §5.4 epoch 규칙을 따른다 (v1.2 — depth 스냅샷 1개 수신만으로 재개하지 않음)

### 5.4 스트림 헬스와 세션 epoch (v1.2)

세 스트림은 역할이 엄격히 분리되어 있으므로(§5.1) 하나만 끊겨도 판정 전제가 깨진다: aggTrade 누락 시 체결 누적이 얼어붙어 FILLED가 PULLED로 오판되고 D3/D4 누적이 불완전해지며, diff 누락 시 벽 상태가, depth 누락 시 접촉 계측이 오염된다. 따라서 연결 단위가 아니라 **스트림 단위**로 규정한다 (combined 연결이라도 개별 스트림만 조용히 멈출 수 있음):

- **헬스 추적**: 스트림별 최종 수신 시각을 상시 기록하고, 워치독이 스트림별 staleness 임계로 감시한다 (§11.1)
- **epoch 정의**: 세 스트림이 모두 healthy한 연속 구간. 어느 하나의 단절·staleness 초과·diff `U`/`u` 갭(§5.1)이 발생하면 epoch가 종료된다
- **epoch 종료 시**: 모든 디텍터(D1~D5) 판정을 보류한다. 단 수신 가능한 스트림의 상태 적재는 계속한다 (레지스트리 절대값 덮어쓰기, trade_window 적재 — 판정만 멈추고 관측은 유지). 활성 intent는 `INTERRUPTED` 마킹(§12), D3/D4 누적 리셋. 벽 레지스트리의 `unconfirmed` 전체 마킹은 **diff 스트림의 공백에만** 적용한다(§12.1) — aggTrade/depth만의 공백은 diff 관측이 유지되므로 레지스트리 값 신뢰도와 무관하다
- **새 epoch 시작**: 세 스트림 모두 구독 확인 + 첫 depth 스냅샷 수신 후. 판정은 이때부터 재개된다
- **재개 직후 한계 (수용)**: trade_window가 다시 찰 때까지(최대 `WINDOW_SECONDS`) D2는 미탐 가능성이 있다 — 부분 데이터는 합계를 과소평가할 뿐 오탐을 만들지는 않는다
- **W 주시 관측기의 취급 (v1.13)**: W(§8 W)의 구역 체결 계측은 "상태 적재"로 분류한다 — epoch 공백 중에도 aggTrade가 살아있는 한 계속된다. 판정 보류 대상은 **무효화 봉 마감 판정뿐**: epoch 공백이 걸친 봉은 판정에서 제외하고 연속 마감 카운트를 리셋한다 (불완전 데이터로 주시를 죽이지 않는 루즈 방향, §8 W)

### 5.5 멀티 거래소 확장 (v1.16 — 거래소별 독립 파이프라인)

**대상과 선정 근거**: Coinbase Exchange `BTC-USD`(1차), Kraken `XBT/USD`·Bitfinex `tBTCUSD`(후속). 선정 축은 현물 거래량 점유율이 아니라 **고래 유동성(±1% 뎁스)** — v1.16 개정 노트의 실측(2026-08-02) 참고. OKX·Bybit는 거래량 상위임에도 뎁스가 바이낸스의 1/3~1/5(MM 호가 위주)라 대형 벽 관측 목적에 후순위. 신규 3곳의 주력 BTC 마켓은 USD 쿼트이므로 바이낸스 USDT 마켓과 가격축이 다르다 — "같은 심볼 확장"이 아니라 **별도 시장의 병행 관측**이다.

**원칙 — 독립 파이프라인, 합산 금지 (§3)**: 벽은 "특정 거래소의 특정 호가창에 놓인 주문"이므로 거래소 간 합산은 개별 주문의 지속/취소/체결 추적(D1의 본질)을 파괴한다. 벽 관측·체결 귀속(`cum_traded_at_level`)·epoch·임계값·판정 전부가 거래소 스코프이고, 한 거래소의 스트림 장애는 그 거래소의 epoch만 종료한다. 거래소 간 접점은 두 곳뿐: 알림 메시지의 venue 표기(§9.3), events DB의 `exchange` 축(§12 — 크로스 거래소 패턴은 사후 분석 소관).

**디텍터 스코프 — D1 + D3 + D5** (사용자 확정 2026-08-02): 벽 수명주기 전체를 신규 거래소에서 동일 재현한다 — D1 출현/소멸(FILLED/PULLED 귀속) + D3 접촉 에피소드(종전대로 로그 전용) + D5 진행률·확정(outbox 포함 전체 적용). **제외**: D2·D4 — 100ms 근접북 스냅샷 케이던스에 로직이 결합돼 있고(D4 은닉 리필의 틱 대조, D2 기준선 부트스트랩) 자체 임계도 M6 튜닝 중. W — 명령 인터페이스(`/watch`)의 거래소 인자 확장은 독립 후속 작업. 이 제외가 아래 어댑터 계약을 성립시킨다.

**어댑터 계약**: 거래소별 신규 코드는 **어댑터**(WS 클라이언트 + 정규화 파서 + epoch 규칙)로 한정한다. 어댑터가 기존 정규화 이벤트 3종(`DepthSnapshot`·`AggTradeEvent`·`DiffDepthEvent`)을 생산하면 상태·디텍터·알림·영속화 계층은 무변경 재사용된다 — 디텍터/상태 계층이 ingestion에서 import하는 것은 이 3종(+`Side`)뿐이라는 기존 경계를 공식 인터페이스로 승격. 구독 3종:

1. **절대잔량 채널** (바이낸스 diff 탭 등가) → `DiffDepthEvent` → wall_registry. 절대 수량 + overwrite 자가치유라는 §5.1 설계 결정 2의 의미론이 세 거래소 모두 성립
2. **체결 채널** → `AggTradeEvent` → trade_window/level_tracker (개별 체결이라 바이낸스 집계 체결보다 세밀 — 의미론 동일)
3. **ticker(최우선호가)** → top-1 `DepthSnapshot` 합성 → D3 접촉 계측·best price. **로컬 풀북 유지 금지** — D2·D4 제외 스코프가 근접북 20레벨 필요를 제거했으므로, §5.1 설계 결정 1이 회피한 드리프트 버그 클래스를 다시 들이지 않는다 (D1+D3+D5의 입력은 셋 다 풀북 불필요: 벽 잔량은 레지스트리가, 접촉은 best price가, 체결 누적은 체결 채널이 공급)

|---|---|---|---|

## 7. 상태 모델 (In-memory State)

| 구조 | 내용 | 갱신 트리거 |
|---|---|---|
| `order_book` | 최신 top-20 스냅샷 `{price: qty}` (bid/ask 각각) | depth 이벤트마다 통째 교체 |
| `level_tracker` | top-20 레벨의 현재 크기 + 체결 귀속: `{price, side, current_size, cum_traded_at_level}` **(v1.2 축소 — `peak_size`·`first_seen_above_threshold`·`active`는 D1의 wall_registry 이관(v1.1)으로 소비처가 사라져 삭제. 레벨 생애주기 추적은 `wall_registry`가 담당)** **(v1.4 예외 — `wall_registry` 등록 가격은 top-20 창 이탈에도 엔트리를 보존한다. 접촉 episode 사이 반등 이탈로 생애 누적이 소실되면 D3 조건 2·D1 귀속이 침묵/왜곡되기 때문. 벽 소멸 시 다음 스냅샷에서 자연 제거, 메모리는 레지스트리 크기로 바운드)** | depth 이벤트(크기), aggTrade(체결 누적) |
| `trade_window` | 최근 `WINDOW_SECONDS` 체결 deque: `(ts, price, qty, aggressor_side)` | aggTrade push, 만료분 pop |
| `volume_baseline` (v1.3) | 최근 `vol_baseline_hours`(24h) 분당 총 테이커 볼륨 버킷 deque + 러닝 합계 — D2 상대 임계의 기준선 | aggTrade push (`exchange_time` 분 버킷 — 단일 스트림 시간창, §11.1), 기동 시 REST klines 1회 부트스트랩 (§8 D2) |
| `intents` | D5 상태기계 인스턴스 목록 (§8 D5) | 디텍터 이벤트 |
| `wall_registry` (v1.1) | 기록 하한(`wall_tracker.record_min_qty_btc`) 이상 대형 레벨: `{price, side, last_qty, peak_qty, first_seen_at, first_seen_above_threshold, last_seen_at, unconfirmed, unconfirmed_since}` — `last_seen_at`은 **판정 미사용**(구 TTL 규칙 폐기(§12.1 v1.2) 이후 관측·튜닝용만 남음. 로직을 걸지 말 것) | **(v1.2)** 신규 가격은 `record_min_qty_btc` 이상일 때만 등록. 이미 추적 중인 가격은 **잔량 값과 무관하게 모든 diff 이벤트로 덮어쓰기**. 잔량 0(명시적 tombstone) 또는 기록 하한 미만 하락 시 소멸 판정(§8 D1 REMOVED) 후 활성 레지스트리에서 제거 |

**level_tracker 스코프 전제 (v1.2)**: D1 FILLED/PULLED 귀속(§8)이 읽는 `cum_traded_at_level`은 top-20 스코프로 충분하다 — 벽이 소진되어 귀속 판정이 일어나는 시점에는 가격이 이미 그 레벨에 접촉해 있어 해당 레벨이 top-20 창 안에 있기 때문이다. 구현 시 이 전제(귀속 판정 시점 = 접촉 상태)에 의존함을 유의한다.

메모리 상한: `trade_window`는 시간 상한, `intents`는 벽 수명(레벨 소멸 시 종국) + 활성 개수 상한(코드 상수)으로 바운드 **(v1.5 — 구 TTL 시간 상한 폐지, §8 D5)**. 재시작 시 상태는 초기화되며(§12 참고), 이는 수용 가능한 트레이드오프다. **예외(v1.1)**: `wall_registry`는 SQLite에 동기화되어 재시작 시 복원된다 — 원거리 벽은 재관측에 시간이 걸려(청취 누적 방식) 초기화 비용이 크기 때문. 복원 직후 처리는 §12 참고.

**수치 표현형 (v1.2)**: 가격·수량은 수신 메시지의 문자열을 `Decimal`로 파싱해 사용하고, 레벨 딕셔너리 키는 정규화된 `Decimal`이다 — 세 스트림의 가격 키를 안정적으로 조인하고 누적 연산 오차를 배제하기 위해 **판정 경로에서 float를 금지**한다 (틱/스텝 정수화는 성능 필요 시의 선택적 최적화로 유보). config의 수치 임계치는 로드 시점에 `Decimal`로 변환해 비교한다.

## 8. 디텍터 명세

모든 임계치는 설정값이며, 괄호 안은 초기 기본값 제안이다.

### D1 — 대형 잔량 발생/제거

**목적**: "1k 이상 bid/ask 발생/제거 시 알림" 요구의 구현 + D5의 입력.

**대상 레벨 (v1.1)**: **벽 레지스트리(`wall_registry`) 전용.** top-20 창은 실측상 현재가 ±$0.2~5에 불과해, 벽이 창 안에 "출현"하는 시점 = 가격이 이미 접촉한 시점이므로 출현 감지 용도로 성립하지 않는다 — top-20(`order_book`/`level_tracker`)은 best price 기준가와 D3/D4의 접촉 시점 정밀 계측에만 사용한다.

**2단 임계치**: 레지스트리에는 `record_min_qty_btc`(100) 이상이면 기록되지만(관측·튜닝 데이터), D1 APPEARED 후보는 그중 `SIZE_THRESHOLD`(1000) 이상만이다. 레지스트리 레벨의 크기 갱신은 이벤트 도착 시점(불규칙)이므로 `PERSIST_SECONDS` 판정은 `SIZE_THRESHOLD` 이상으로 관측된 최초 시각(`first_seen_above_threshold`) 기준으로 계산한다. `unconfirmed` 상태인 레벨은 새 이벤트로 확인되기 전까지 APPEARED 발화를 억제한다(§12).

**발생(APPEARED) 조건** — 다음을 모두 만족하는 순간 발화:
1. 어떤 레벨의 `last_qty ≥ SIZE_THRESHOLD` (1000 BTC — 확정값, §15 #1. Binance 현물에서 "전달력 있는" 매수/매도 유동성 기준)
2. 그 상태가 `PERSIST_SECONDS`(3s) 이상 연속 유지 ← **스푸핑 1차 필터**
3. 해당 레벨에 대해 미발화 상태 (레벨당 1회, 레벨이 임계 밑으로 내려갔다 다시 올라오면 리셋)

**알림 1회 규칙 (v1.8)**: 텔레그램 발송은 임계 스트릭(`first_seen_above_threshold` 값)당 1회다. 재시작 복원·epoch 재시작 후의 APPEARED 재발화는 D5 인텐트 재등록(§8 D5)을 위한 내부 이벤트로 유지하되, 발송은 `walls.appeared_alerted_since`(발송 시 스트릭 값 기록·영속, §12.1)와의 비교로 억제한다(억제 시 로그만). 스트릭 값이 바뀐 재돌파(임계 하회 후 재상승)와 REMOVED 후 재출현은 새 등장으로 발송한다.

**제거(REMOVED) 조건** — 활성 레벨의 `last_qty < SIZE_THRESHOLD × EXIT_RATIO`(0.5)로 하락 시, 감소 원인을 판정하여 발화:
- `cum_traded_at_level ≥ (peak_qty − last_qty) × FILL_ATTRIBUTION`(0.7) → **`FILLED`** (실체결로 소진)
- 그 외 → **`PULLED`** (취소/스푸핑 추정)

**귀속 한계 (v1.2 수용)**: `cum_traded_at_level`은 레벨 생애 누적이므로, 흡수→리필을 반복한 벽이 나중에 pull되면 과거 episode의 체결이 최근 하락분(`peak_qty − last_qty`)에 귀속되어 FILLED로 과대 판정될 수 있다. 이 분류가 가르는 것은 D5의 로그 전용 상태 구분(`PARTIALLY_EXECUTED` vs `INTENT_WITHDRAWN`, §8 D5)뿐이고 알림에는 영향이 없으므로, 교정 규칙 없이 수용한다 — M6에서 스푸핑 비율 통계를 해석할 때 유의.

**레지스트리 소멸 규칙 (v1.2)**: `record_min_qty_btc`는 **신규 가격의 등록 게이트일 뿐**, 이미 추적 중인 가격의 diff 이벤트는 잔량 값과 무관하게 항상 처리한다. 잔량 0은 명시적 tombstone으로 소멸 처리하고, `0 < 잔량 < record_min_qty_btc`로 하락한 경우에도 동일하게 — D1 활성 레벨이었다면 REMOVED 판정(FILLED/PULLED)을 먼저 수행한 뒤 — 활성 레지스트리에서 제거한다. 이 규칙이 없으면 1,200 → 50 BTC 감소 이벤트가 "하한 미만·0 아님"으로 무시되어 유령 벽(1,200)이 잔존하고, `last_qty`가 갱신되지 않아 REMOVED 판정 자체도 발화하지 못한다.

**평가 시점**: diff 탭 이벤트 도착마다 갱신(주기 불규칙 — 해당 가격에 변경이 있을 때만), 발화는 지속시간 타이머로 게이트.

### D2 — 볼륨 버스트 (v1.3 — 에피소드형 상대 임계)

**목적**: "특정 시간 내 일정 볼륨 발생 시 알림" 요구의 구현. 발생 순간의 실시간 통지(온셋)와 종료 후 결과 정리(요약)를 분리하고, 임계를 유동성 국면에 자동 추종시킨다.

**기준선 (상대 임계)**: 최근 `VOL_BASELINE_HOURS`(24h)의 분당 총 테이커 볼륨 평균 (§7 `volume_baseline`). 발화 임계:

```
THR = max(VOL_FLOOR(30 BTC), VOL_MULTIPLIER(10) × 분당 기준선)
```

절대 하한 `VOL_FLOOR`는 침체기에 기준선이 낮아져 소액 체결로 발화하는 것을 막는다. 근거 실측(2026-07-12 백테스트, 6/29~7/12 1분봉): 현 유동성(24h ~12k BTC)에서 THR ≈ 80~190 BTC로 구판 고정 100 BTC와 동급이나, 발화가 하루 ~17회 → ~7 에피소드로 줄면서 사용자 지정 스파이크/흡수 9개 구간은 전부 유지. 구판 고정 `VOL_THRESHOLD`는 폐기 — 유동성이 배수로 변하는 국면마다 수동 재설정이 필요했다.

**워밍업**: 기동 직후 기준선 창이 비므로 REST `GET /api/v3/klines?interval=1m` 1440분치로 1회 부트스트랩한다. 실패 시(지오블록·레이트리밋 등) 로그를 남기고 창이 자연히 찰 때까지 D2 판정을 보류한다 — 인메모리 상태 복원(§12 금지 원칙)이 아니라 외부 소스 재조회이므로 원칙과 무관.

**온셋 (에피소드 시작)**: epoch 활성 중 60초 창(`WINDOW_SECONDS`)의 **총** 테이커 볼륨(매수+매도 합산) ≥ THR인 순간 에피소드를 시작하고 온셋 알림을 발화한다. v1.2까지의 방향 분리 트리거는 폐기 — 방향 정보는 성격 라벨로 이동한다 (실측상 대형 15m 고볼륨 봉의 다수가 양방향 공방으로, 한쪽 방향만으로는 임계에 못 미쳐 놓친다).

**에피소드 종료**: 60초 창 총합 < `THR × EPISODE_EXIT_RATIO`(0.5)로 식으면 잠정 종료. 이후 `EPISODE_MERGE_MINUTES`(10분) 내 재점화하면 같은 에피소드로 계속(온셋 재발화 없음), 재점화 없이 경과하면 확정 종료하고 요약 알림을 발화한다 — 누적 볼륨(기준선 대비 배수 병기)·델타(매수/매도 분해)·지속시간·가격 변화(시가→종가, 고저). 병합 창은 지속 고볼륨이 여러 파동으로 오는 패턴을 하나의 에피소드로 묶는다 (백테스트: 45분 지속 사례가 병합 없이는 4조각으로 파편화).

**성격 라벨**: 델타비 `r = |매수 − 매도| / 총합` (온셋은 60초 창, 요약은 에피소드 누적 기준):

- `r ≥ DELTA_DIRECTIONAL_RATIO`(0.5) → **방향성** (매수/매도 명시)
- `r ≤ DELTA_BALANCED_RATIO`(0.2) → **양방향** (흡수성 후보)
- 그 사이 → **혼합**

흡수의 확정 판정은 오더북 반응을 보는 D3의 몫이며 D2는 테이커 흐름의 성격만 라벨한다 — 가격 변화를 병기해 "매도 델타가 큰데 가격이 안 밀림 = 흡수 후보"를 수신자가 메시지에서 직접 읽을 수 있게 한다.

**평가 시점**: aggTrade 수신마다 + 1s 주기 틱 (체결이 끊겨도 창이 식으면 종료 판정이 진행되도록). epoch 종료 시 진행 중 에피소드는 폐기한다 (요약 미발송, 로그만 — 부분 누적은 신뢰 상실, §5.4). 분 버킷 적재는 상태 계층으로 계속된다.

### D3 — 흡수 (케이스 1)

**전제**: 가격 P에 D1 활성(APPEARED) 레벨 존재.

**접촉 episode (v1.2)**: 베스트 프라이스가 P에 도달한 시점부터 (a) 반등으로 P에서 이탈, (b) 관통 확정, (c) 레벨 소멸 중 하나까지의 구간. 판정은 스냅샷 단발이 아니라 **episode 단위**로 수행한다. 하나의 레벨에 복수의 접촉 episode가 있을 수 있으며, `cum_traded_at_level` 누적은 기존대로 레벨 생애 기준이다.

**조건** — 모두 만족 시 발화:
1. 접촉 episode 존재 (bid 레벨이면 best bid가 P까지 하락 접촉)
2. P에서의 공격적 체결 누적 `cum_traded_at_level ≥ ABSORPTION_MIN`(표시 크기의 30%)
3. 해당 episode 동안 가격이 P를 관통하지 않음. **관통 판정 (v1.2 개정)**:
   - **bid 벽**: episode 중 sell-aggressor 체결가 `< P` 발생 (주 신호 — 체결은 확정적 증거), 또는 `best_bid < P`가 `PIERCE_PERSIST_SNAPSHOTS`(2) 연속 스냅샷 지속 (보조 신호 — 아이스버그 리필 사이 잔량이 순간 0이 되는 플리커를 관통으로 오판하지 않도록 지속성을 요구)
   - **ask 벽**: 대칭 — buy-aggressor 체결가 `> P` 발생, 또는 `best_ask > P` 지속
   - 관통 확정 시 해당 episode에서 D3는 발화하지 않는다 (레벨 소멸·intent 처리는 D1/D5 경로)
   - 구 기준(bid 벽에 best **ask** `< P`)은 폐기: 관통의 충분조건이지만 지연 신호다 — bid 측이 P 아래로 무너져도 best ask는 P 위에 남을 수 있어, 실제 돌파를 "비관통"으로 오판해 흡수 이벤트를 D5에 잘못 공급할 수 있다

**발화 시점 (v1.4)**: episode가 **비관통(반등/소멸)으로 종료되는 시점**에 조건 충족 여부를 확정 판정해 episode당 최대 1회 발화한다. 조건 충족 즉시 발화하면 이후 같은 episode에서 관통될 때 이미 낸 이벤트가 사후에 거짓이 되어 조건 3의 "관통 시 무발화"와 충돌 — D3는 로그 전용이고 D5 케이스 1은 자체 누적 감시(§8 D5)라 종료까지의 지연 비용은 없다.

**산출**: 흡수량, 실현률(`cum_traded / 등록 시 표시크기`).

### D4 — 레벨 흡수 방어 (v1.11 재설계, 구 아이스버그/리필)

> **(v1.11) 재설계 확정, 구현 대기** — 구 명세("케이스 2의 재료", episode 스코프 아이스버그 감지)는 케이스 2 폐지와 함께 대체됨. 본 절이 재구현의 기준이며, 구현 완료까지 배선 제외(v1.6) 상태를 유지한다. 구 명세가 필요하면 v1.10 이전 리비전 참고.

**목적**: 특정 레벨이 **먹히면서도 계속 다시 채워지며 가격을 방어하는 행동**(반복 리필·지속 흡수)을 감지해 독립 통지한다. D1 임계(1000 BTC) 미만의 준임계 벽이 주 대상이다 — 근거 실측: 07-14 61k 상위 구간 리필, 07-17 62.8k(peak 220 BTC, ~200 BTC급 반복 리필로 방어 후 소멸 — 현 계층 구성에서 완전 무통지였던 구조적 사각). 귀속·의도 해석은 하지 않는다: 관측 수치만 통지하고 해석은 수신자 몫 (v1.11 원칙).

**대상**: 벽 레지스트리 추적 레벨 **전체** (관측 하한 `record_min_qty_btc` 100+ — 신규 인프라 없음). D1 활성 벽도 포함한다 — D5 케이스 1(원시 체결 누적 대 표시 의도)과 D4(리필로 입증된 방어)는 같은 벽에서도 서로 다른 관측이므로 병행 발화를 수용한다 (중복 부담은 M6 튜닝에서 재검토).

**추적 단위 — 스트릭**: 레지스트리 등록(하한 통과)부터 소멸(tombstone/하한 미달, §8 D1 소멸 규칙)까지의 활성 기간. 누적은 **스트릭 생애 기준**이며 접촉 episode 사이 리셋되지 않는다 (D1 v1.8 스트릭·D5 v1.9 래치와 대칭). **기준크기 R** = 등록 시점 `last_qty`로 고정 — D5의 S와 같은 논리(순간 스파이크·성장분으로 분모가 흔들리지 않게, "등록을 촉발한 표시 크기" 기준). 재등록 = 새 스트릭, 누적 리셋.

**흡수량 산식 — 리필로 입증된 체결만 집계**: 원시 `cum_traded_at_level`을 쓰지 않는다. 장시간 횡보 회전(다수 참여자 주문의 소진과 무관한 재유입)도 체결 총량은 크게 누적되므로, 총량 기준은 저유동성 횡보 구간에서 오발화한다 — 이는 v1.2가 D4 구 산식을 폐기한 것과 같은 "경로 소실" 결함이다. 대신 두 성분만 합산한다:

```
absorbed = Σ refill_added (① 가시 리필) + Σ hidden_refill (② 은닉 리필)
```

- **① 가시 리필** (v1.2 산식 유지): depth 스냅샷 간 양의 델타 중, 직전 `REFILL_WINDOW_MS`(500ms) 이내 해당 레벨 aggTrade 체결이 있었던 것만 인정. 체결과 무관한 재유입(횡보 회전의 신규 주문)은 페어링 실패로 자연 배제
- **② 은닉 리필** (v1.11 신설 — v1.6 한계 ②의 네이티브 아이스버그 사각 해소): **스냅샷 틱(100ms) 단위**로 `max(0, 틱 내 해당 레벨 체결량 − 틱 내 표시잔량 감소분)`을 합산. 거래소 엔진이 소진과 원자적으로 재표시하는 네이티브 아이스버그는 양의 델타가 안 생겨 ①에 안 잡히지만, "체결은 있는데 잔량이 안 줄어든 틱"으로 나타난다. **반드시 틱 단위로 대조한다** — episode/스트릭 전체를 뭉뚱그려 `체결 총량 − 잔량 감소 총량`으로 계산하면 무관한 신규 주문이 끼어들어 경로 소실 결함이 재발한다. 횡보에서는 체결이 실제로 잔량을 깎으므로 틱별 mismatch ≈ 0. 수용 오차: 같은 100ms 틱에 무관한 신규 주문이 체결과 우연히 겹치면 소량 과대 계상되나, 오차가 틱 단위로 국소화되므로 수용 (M6 로그 리뷰로 검증). **1틱 이월 보정 (v1.12)**: 스트림 순서 역전으로 체결과 그 감소를 반영한 스냅샷이 다른 틱에 떨어지면 감소분은 앞 틱에서 클램프로 버려지고 체결은 뒤 틱에서 은닉 리필로 오인된다 — 오차가 양의 방향으로만 누적되므로, 직전 틱의 체결 없는 감소 초과분 `carry = max(0, 직전 틱 표시잔량 감소분 − 직전 틱 체결량)`을 차감한다: `hidden_refill = max(0, 틱 내 체결량 − 틱 내 표시잔량 감소분 − carry)`. 이월은 직전 1틱 한정 — 오차 국소화 원칙 유지

**발화 조건 (방어 감지, `DEFENSE_DETECTED`)** — 모두 만족 시 스트릭당 1회:

1. `absorbed ≥ ABSORB_MULTIPLE(M) × R` — 배수 기준이라 고정 BTC 상수가 없고 벽 크기에 자동 스케일. M 초기값 2.0 (잠정 — M6 튜닝 대상)
2. 흡수 인정 이벤트 수(①의 페어링 쌍 + ②의 양성 틱) ≥ `ABSORB_MIN_EVENTS`(5) — 단발 틱 우연 겹침에 의한 원샷 오발화 방지 (구 `ICEBERG_MIN_TRADES`의 "시간에 걸친 반복" 취지 계승)
3. 현재 관통 상태가 아닐 것 — D3 관통 판정(§8 D3 조건 3) 재사용. 유동성 폭발로 많이 체결됐지만 뚫린 레벨은 방어가 아니다
4. 레벨이 레지스트리 활성 상태일 것 (스트릭 정의상 자동 충족)

**래치·진행·종결 (v1.9 대칭)**:

- 첫 발화 후 **래치** — 스트릭이 살아있는 한 추적 지속, 이후 absorbed가 `R × ABSORB_PROGRESS_STEP`(0.5) 증가할 때마다 진행 발화(`DEFENSE_PROGRESS`), **상한 없음** (2.0×, 2.5×, 3.0×, …)
- 스트릭 종료(레벨 소멸/하한 미달) 시: 래치된 방어는 종결 통지 `DEFENSE_CLOSED` 1회(최종 absorbed·배수 동반) — 준임계 벽은 D1 REMOVED 알림 대상이 아니므로 방어 붕괴/소진을 D4가 직접 통지해야 한다. 미래치 스트릭의 소멸은 로그만
- epoch 종료(§5.4): 누적 신뢰 상실 — 누적 리셋, 래치된 방어는 `DEFENSE_INTERRUPTED`(로그만) 기록. 재시작·중단으로 카운트가 끊기는 예외는 처리하지 않는다 (v1.9 수용 한계와 동일 — 사용자 확정 원칙)
- **epoch 시작 시 스트릭 재개시 (v1.12)**: 새 epoch 시작(재시작 복원 포함) 시 활성 레지스트리 벽 전체에 새 스트릭을 개시하고, R = 그 시점 `last_qty`로 재고정한다 — 스트릭 개시를 신규 등록에만 걸면 복원 벽·epoch 생존 벽이 완전 소멸 후 재등록 전까지 D4 사각이 되기 때문 (장수 준임계 벽이 주 표적, v1.5가 D5에서 폐지한 "죽은 창"과 같은 부류)

**산출**: 레벨, 방향, 기준크기 R, absorbed(①/② 분해), 흡수 배수, 흡수 인정 이벤트 수, 스트릭 시작 이후 경과시간.

**관측 기록 (v1.11 — 배포 후 검증·튜닝의 필수 데이터)**: 발화 이벤트(위 `DEFENSE_*`)는 다른 디텍터처럼 `_emit` 경유 JSON-lines에 전 필드로 남지만, 그것만으로는 판정 임계 **미달** 구간이 무기록이 되어 튜닝이 불가능하다(07-17 62.8k 무기록과 같은 구조의 공백). 따라서 발화와 별개로 다음을 구조화 로그로 기록한다:

- **흡수 인정 이벤트 단위 로그** — 인정 이벤트(① 페어링 쌍 / ② 은닉 틱)마다 1줄: 스트릭 식별자(price·side·등록 시각), 종류(가시/은닉), 수량, 근거값(①은 체결→회복 페어링 지연 ms, ②는 틱 내 체결량·표시감소분), 누적 absorbed. 용도: `REFILL_WINDOW_MS` 튜닝, 가시/은닉 분해의 타당성 검증, 흡수 발생 횟수·증감 과정의 원천 데이터
- **스트릭 종료 요약 로그** — 스트릭 종료 시 absorbed > 0이면 **발화 여부와 무관하게** 1줄: 최종 absorbed(①/② 분해), 최대 도달 배수, 이벤트 수, 스트릭 지속시간, R. 용도: near-miss 분포(예: 1.2×에서 끝난 벽의 빈도)가 `ABSORB_MULTIPLE` 조정의 직접 근거
- 로그 볼륨은 자연 바운드 — 인정 이벤트는 레지스트리 추적 레벨에서 접촉 중 체결이 있고 리필/mismatch가 실재할 때만 발생하므로, 별도 스로틀 없이 전건 기록한다

**D3/D5와의 관계**: D3(D1 벽 전용, episode 스코프, 로그 전용)는 무변경. D4는 더 이상 D5에 공급하지 않는다 — 케이스 2 폐지로 D4는 독립 알림 디텍터다.

### D5 — 인텐트→실체결 상태기계 (핵심 신호)

D1~D4는 재료이고, 최종 사용자 신호는 D5가 생성한다.

**상태 전이 (v1.11 — 케이스 2 분기 폐지)**:

```
                    D1 APPEARED (크기 S 기록)
                          │
                          ▼
                  INTENT_REGISTERED
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
       가격 도달 +               가격 미도달 +
       레벨 체결 누적            레벨 PULLED
       ≥ S × REALIZE_PCT
              │                       │
              ▼                       ▼
    EXECUTION_CONFIRMED        INTENT_WITHDRAWN
     (케이스 1, 알림 발송)       (스푸핑, 로그만)

수명 (v1.5): 인텐트는 만료되지 않는다 — 벽이 살아있는 한 유지, 종국은
레벨 소멸·epoch 종료로만 발생 (구 INTENT_TTL 폐지, 개정 이력 참고.
v1.9 — 케이스 1 충족은 종국이 아닌 래치: 확정 발화 후에도 인텐트 유지.
v1.11 — 구 케이스 2 분기(EXECUTION_INFERRED_ABOVE)는 폐지: 상위 구간

```

**파라미터**: `REALIZE_PCT`(0.6). (v1.11 — 구 `REALIZE_PCT_ABOVE`·"상위 구간" 정의는 케이스 2 폐지로 삭제)

**등록 크기 S (v1.2 명시)**: S는 **D1 APPEARED 발화 시점의 `last_qty`로 고정**한다 (지속 필터 통과 직후의 레지스트리 관측값). peak를 쓰지 않는 이유: 순간 스파이크가 실현률 분모를 부풀린다. 등록 후 벽이 성장/축소해도 S는 갱신하지 않는다 — 실현률의 기준은 "등록을 촉발한 표시 의도"이며, 이후 크기 변화는 로그/DB(peak 등)로만 기록한다 (수용 한계).

**종국 상태 목록 (v1.2, v1.5에서 EXPIRED 폐지, v1.9에서 CONFIRMED 래치화·CONFIRMED_CLOSED 신설, v1.11에서 INFERRED_ABOVE 폐지)**:

| 상태 | 알림 | 의미 |
|---|---|---|
| `EXECUTION_CONFIRMED` | 발송 | 케이스 1 — 레벨 체결 임계 충족. **(v1.9) 종국이 아닌 래치**: 발화 1회 후 인텐트는 유지되어 진행률 감시가 계속된다 |
| ~~`EXECUTION_INFERRED_ABOVE`~~ | — | **폐지 (v1.11)** — 케이스 2 자체가 폐지됨 (v1.6 임시 비활성 → 영구). 상위 구간 활동은 D4 흡수 방어가 대체 |
| `CONFIRMED_CLOSED` | 로그만 | (v1.9) 확정 래치된 인텐트의 벽 소멸 — 최종 실현률 기록. 소멸 통지는 D1 REMOVED 알림이 담당하므로 미발송 |
| `PARTIALLY_EXECUTED` | 로그만 | FILLED 귀속 소멸 + 실현률 미달 (부분 흡수 — 스푸핑 아님) |
| `INTENT_WITHDRAWN` | 로그만 | PULLED 귀속 소멸 (철회/스푸핑 추정. v1.11 — "케이스 2 미달" 단서 삭제) |
| `INTERRUPTED` | 로그만 | epoch 종료 (§5.4, §12 — 누적치 신뢰 상실). 확정 래치된 인텐트도 동일 (최종 실현률 동반) |

~~**케이스 2 집계 방식**~~ → **폐지 (v1.11)**: 상위 구간 리필의 하위 인텐트 귀속 집계는 폐지. 07-17 실측이 보여줬듯 상위 구간 리필은 "무관한 노이즈"가 아니라 임계 미달의 독립적 의도일 수 있어, 합산(오귀속)도 폐기(무통지)도 아닌 **자기 레벨에서의 독립 신호**(§8 D4)로 전환한다.

**판정 의미 (v1.2 명시)**: 공개 스트림에는 주문 소유자·maker 주문 ID가 없고 aggTrade도 단일 taker 주문 기준 집계일 뿐이므로, 특정 주체로의 체결 귀속은 데이터상 불가능하다.
- **케이스 1의 "확정"** = "해당 가격 레벨에서 임계 이상의 체결이 실제 발생함"의 확인이다. 같은 가격에 복수 주문이 공존할 수 있고 큐 위치도 알 수 없으므로, 원래 표시된 대형 주문 자체가 체결되었다는 확인은 아니다.
- ~~케이스 2의 "추정(inferred)" 등급~~ → **폐지 (v1.11)**: 귀속 불확실성을 "추정" 등급 표기로 완화하는 접근 자체를 폐기 — 귀속 해석을 하지 않는 것으로 대체 (§8 D4).

**소멸 시 종국 평가 (v1.2, v1.11에서 케이스 2 분기 삭제)**: 등록된 인텐트의 레벨이 소멸하면(D1 REMOVED, tombstone, 기록 하한 미만 하락 — §8 D1 소멸 규칙) TTL이나 다음 이벤트를 기다리지 않고 **즉시** 종국 상태를 평가한다. **(v1.9)** 이미 확정 래치된 인텐트는 아래 분류와 무관하게 `CONFIRMED_CLOSED`(로그만)로 마감한다. 미확정 인텐트의 소멸 원인은 세 가지로 구별한다:

1. **가격 도달 + 레벨 체결 누적 충족** → `EXECUTION_CONFIRMED` (케이스 1, 그 자리에서 흡수)
2. **D1 `FILLED` 귀속 + 실현률 미달** → `PARTIALLY_EXECUTED` (로그만) — 부분 흡수 후 소멸. 스푸핑이 아니므로 `INTENT_WITHDRAWN`과 구분한다 (혼합 시 M6 스푸핑 비율 통계가 오염됨)
3. **D1 `PULLED` 귀속** → `INTENT_WITHDRAWN` (로그만) — 철회/스푸핑 추정

모든 종국 레코드에는 레벨 실현률을 남긴다. 이로써 흡수(케이스 1)에 의한 소멸은 벽 소멸 알림(D1 REMOVED, 기본 on — v1.10)과 별개로 D5 확정 알림이 **보장**되어, "흡수에 의한 소멸"임을 알 수 있다.

**평가 트리거와 우선순위 (v1.2, v1.5에서 TTL 트리거 삭제, v1.11에서 INFERRED 삭제)**: D5 평가 시점은 (a) 레벨 체결·디텍터 이벤트 갱신, (b) 레벨 소멸, (c) epoch 종료(§5.4)다. 한 평가 사이클에서 복수 조건이 동시 충족되면 `EXECUTION_CONFIRMED` > `PARTIALLY_EXECUTED` > `INTENT_WITHDRAWN` 순으로 상위 상태가 이긴다. 단 **epoch 종료는 이 순서와 무관하게 즉시 `INTERRUPTED`** — 그 시점의 미확정 누적치는 신뢰를 상실했으므로 확정으로 승격하지 않는다 (임계는 넘는 순간 즉시 발화하므로, epoch 종료 전에 충족된 확정은 이미 발화되어 있다).

**진행률 알림 (v1.2, v1.11에서 케이스 2 계열 삭제 — 단일 계열)**: 등록된 인텐트에 대해, 실현률(레벨 체결 누적/S)이 `PROGRESS_STEP_PCT`(0.2) 경계를 넘을 때마다 진행률 알림을 1회 발화한다.
- 발화는 `(인텐트, 경계값)`당 1회. **(v1.9)** 확정 **전**에는 확정 임계(`REALIZE_PCT` 0.6) 도달 경계를 확정 알림 자체가 대체하므로 기본값 기준 실효 경계는 20%, 40%다. 확정 **후**(케이스 1 래치)에는 경계 상한 없이 계속 발화한다 — 80%, 100%, 120%, … (100% 초과 = 리필분 재흡수, 그 구간의 총 흡수량 가시화)
- 진행률 알림의 dedup 키는 `(intent_id, 계열, 경계값)`이며 시간 쿨다운을 적용하지 않는다 (§9.2 v1.2) — 빠른 흡수에서 연속 경계 도달이 쿨다운에 먹히면 기능이 성립하지 않음
- on/off는 알림 정책(`alerts.send_d5_progress`, 기본 on)에서 제어 — 기존 `send_d1`/`send_d2` 관례와 동일. 재시작 시 인텐트와 함께 진행률 커서도 소멸 (§12 원칙과 일치, 복원하지 않음)
- 구현 순서: M4 코어 상태기계(전이·종국 평가) 단위 테스트 통과 후 마지막 항목으로 추가 — 구조 변경 없는 순수 추가 기능이므로 선행 준비 불필요

### W — 주시 레벨 관측기 (v1.13 신설)

> **디텍터가 아니다** — 임계 판정 없이, 사용자가 지정한 가격 구역의 체결을 계측해 주기 보고만 한다. v1.11 원칙("관측은 기계가, 의도 해석은 수신자가")의 직접 적용: 어느 레벨이 중요한지(해석)는 사용자가 텔레그램 명령(§9.5)으로 공급하고, 기계는 그 구역의 관측 수치를 돌려보낸다. D5에 공급하지 않고 다른 디텍터와 상호작용하지 않는다.

**목적**: 대형 표시 잔량이 없어 D1/D4/D5의 대상이 아닌 지지/저항 레벨의 흡수를 가시화한다. 배경(2026-07-23): 07-22~23 65.6k 지지 테스트의 흡수 반응이 텔레그램에 무통지 — 표시 벽 기준 계층(D4 v1.11 포함)의 구조적 사각. 설계 검증 사례 5건(사용자 제시 차트, 결정 기록 2026-07-23): 65.6k 저항→돌파→지지→이탈 시퀀스(07-15~07-23), 64.9k 40시간 저항(65~66k 구간 내 일시 돌파 포함), 62.8k 0.5% 이탈 후 시간봉 꼬리 회복, 63.8k 지지 + 07-20 17:30 급락.

**등록**: `/watch <price>`(폭 0 구역) 또는 `/watch <lo>-<hi>`. 내부 표현은 항상 구역 `[lo, hi]`. 범위 입력의 근거: 64.9k 사례는 단일가 주시였다면 일시 돌파 마감에 조기 무효화 — 사용자가 "65~66k 큰 저항구간"으로 보는 것을 그대로 입력하게 한다. 방향(지지/저항)은 입력받지 않는다 — 역할은 가격 위치에서 자동 유도.

**접촉 밴드와 계측 범위의 분리 (핵심 구조)**:

- **접촉 밴드** `[lo×(1−w), hi×(1+w)]`, w = `CONTACT_BAND_PCT`(0.1%): 테스트 회차(episode) 경계와 리포트 활동 게이팅 **전용** — 계측 상한이 아니다.
- **계측 범위는 동적·단방향 무제한**: 지지 테스트 중에는 체결가 `≤ hi`인 모든 aggTrade를 taker 방향 분리로 집계하고 저점(excursion)을 추적한다. 저항 테스트는 대칭(체결가 `≥ lo`, 고점). 깊이 캡을 두지 않는 근거(사용자 확정): 주시가부터 저점까지의 체결은 사실상 전부 흡수 체결량이며, 07-20 17:30급 급락도 밴드 튜닝 실패로 놓치는 것이 아니라 무효화 확정 시점까지 전부 집계된 뒤 최종 리포트에 담긴다 — 계측의 바운드는 공간(밴드)이 아니라 시간(무효화 봉 마감, 최대 `CONFIRM_CLOSES`봉)이다.
- **원시 체결 총량 사용이 v1.11의 총량 기각과 충돌하지 않는 이유**: D4의 기각은 "기계 임계 판정의 입력"으로서였다(횡보 회전 오발화). W는 판정이 없고 수치를 그대로 보고한다 — 횡보 회전(양측 균형)과 방어 흡수(편중 + 가격 유지)의 구분은 리포트의 매수/매도 분해·인터벌/누적 병기로 수신자가 한다.

**역할과 테스트 회차**:

- 회차 시작 = 접촉 밴드 진입, 종료 = 밴드 이탈. **회차 종료는 주시를 끝내지 않는다** — 일시 관통도 반등 이탈도 주시는 유지되고, 누적·excursion은 회차를 관통하는 **주시 생애 기준**이다 (64.9k "두 차례에 걸친 흡수" 커버. D1 스트릭·D5 래치·D4 스트릭과 대칭).
- 역할 = 회차 시작 시점 최근 체결가 vs 구역: 구역 위 → 지지 테스트, 아래 → 저항 테스트. 회차마다 재판정한다(마감 미확정 관통 후 반대편 재진입 허용). 범위 주시를 구역 내부에서 등록한 경우만 "대기" — 첫 구역 이탈 후 재진입부터 회차 개시.

**무효화 (자동 해소)** — 역할 반대편으로의 **봉 마감(몸통)** 기준, 꼬리는 무시한다:

- 지지: `CONFIRM_TIMEFRAME`(15m) 봉 마감가 `< lo×(1−INVALIDATE_BUFFER_PCT)`가 `CONFIRM_CLOSES`(2)회 **연속** → 이탈 확정. 저항은 대칭(`> hi×(1+버퍼)`) → 돌파 확정. 기본값 15m×2는 사용자 확정(2026-07-23) — 1h×1 대안과 유사한 강건성에 더 빠른 확정, 전부 config라 추후 조정 가능. 꼬리 무시의 근거: 62.8k 사례(0.5% 이탈 후 시간봉 꼬리 회복 = 레벨 유지)와 통상 관행(SFP/스프링 — 꼬리 관통 + 마감 복귀는 붕괴가 아니라 레벨 검증) 정합.
- 확정 시 최종 리포트 1회 후 주시 **종료**. 역할 반전 유지(저항 돌파 → 지지 감시 전환)는 기각(§16) — 재등록은 명령 1개인 반면, 반전 유지는 넓은 레인지 내 단일가 주시에서 핑퐁 소음이 된다.
- 자동 기준은 루즈하게, 수동 해소(`/unwatch`)는 언제든 — 이 병행이 전제다.
- **봉 조립**: aggTrade `T`(거래소 시각)를 15m/1h 경계로 버킷팅해 자체 조립한다 — 신규 스트림 없음(§5.1 3-스트림 역할 분리 유지, kline 구독 기각 §16). 마감가 = 버킷 내 마지막 체결가 (§11.1 시계 정책).
- **epoch 상호작용**: §5.4 — 계측은 상태 적재로 지속, 무효화 판정만 보류(공백 낀 봉 제외 + 연속 카운트 리셋). 수용 한계: 공백 중 가격이 구역을 완전히 통과하면 무효화 없이 역할만 바뀐 채 재개될 수 있다 — 리포트의 역할 표기로 수신자가 인지, 필요 시 수동 해소.

**발송 (§9.1)**: 첫 접촉(회차 1 시작) 1회 + **주기 리포트**(주력, `REPORT_INTERVAL_SECONDS` 600s — 직전 리포트 이후 계측 체결이 있거나 현재 밴드 내일 때만 발송하는 활동 게이팅: 64.9k급 40시간 주시가 무활동 스팸이 되지 않게) + 무효화 확정 시 최종 리포트 1회(감시 종료의 무통지는 조용한 실패(§11.1)의 사용자 버전 — 발송 보장은 §9.4) + `/watching` 온디맨드 현황. 리포트 필드: 구역·역할·회차 수·첫 접촉 후 경과·현재가·excursion 극값·인터벌/누적 taker 매도/매수·진행 중 이탈 마감 연속 카운트(예: "15m 이탈 마감 1/2")·구역 내 레지스트리 벽(D2 근접 벽 라인 재사용)·epoch/재시작 공백 플래그. 최종 리포트엔 종료 사유(돌파/이탈/수동)를 병기한다.

### 9.2 스팸 억제 (v1.2 — 범위 분리)

억제 메커니즘은 알림 종류별로 분리한다. 가격 버킷 쿨다운을 전 알림에 일괄 적용하면, 같은 버킷의 서로 다른 intent 두 개가 5분 내 확정될 때 두 번째 **핵심** 알림이 삼켜진다 — D5 종국 알림은 intent당 1회만 발생하므로 시간 쿨다운은 중복을 막는 게 아니라 진짜 신호만 잃는다.

- **D1 (노이즈 억제 전용)**: dedup 키 `(detector, side, price_bucket)` — `price_bucket`은 가격을 `BUCKET_SIZE`(50 USDT)로 양자화. 키당 쿨다운 `ALERT_COOLDOWN`(300s). **(v1.15 페어링 보장)** 단, APPEARED 알림이 실제 발송된 스트릭(마킹 `walls.appeared_alerted_since` 일치)의 REMOVED는 쿨다운을 우회해 무조건 발송하며 deduper에 기록하지 않는다 — "출현을 보고했으면 소멸도 반드시 보고"의 불변식. 쿨다운은 미발송 스트릭의 REMOVED와 APPEARED에만 적용된다 (발송량 상한: 소멸 ≤ 출현)
- **D2 (v1.3 — 시간 쿨다운 미적용)**: 에피소드당 온셋 1회·요약 1회가 구조적으로 보장되고, 종료 후 `EPISODE_MERGE_MINUTES` 병합 창이 재점화 스팸을 흡수한다. 구판의 `(방향)` 쿨다운·가격 버킷 dedup은 에피소드 모델로 대체
- **watchdog**: dedup 키 `(알림 종류, 스트림)` + `ALERT_COOLDOWN` (플래핑 스팸 방지)
- **D5 종국 알림**: dedup 키 `(intent_id, terminal_state)`, **시간 쿨다운 미적용** — 이 키는 억제용이 아니라 재전송 멱등성 보장용이다 (§9.4 outbox 연동)
- **D5 진행률 알림**: dedup 키 `(intent_id, 경계값)`, 시간 쿨다운 미적용 — 같은 경계의 중복 발화만 차단 (v1.11 — 케이스 2 폐지로 계열 항 삭제)
- **D4 흡수 방어 알림 (v1.11)**: dedup 키 `(price, side, 스트릭, 이벤트 종류/경계배수)`, 시간 쿨다운 미적용 — 감지·종결은 스트릭당 1회가 구조적으로 보장되고(래치), 진행은 경계 중복만 차단 (D5 진행률과 동일 원리)
- **W 주시 리포트 (v1.13)**: 가격 버킷 쿨다운·dedup 미적용 — 자체 케이던스(`report_interval_seconds` + 활동 게이팅, §8 W)가 억제 메커니즘. 수신 명령의 성공/오류 응답(§9.5)도 동일 (사용자 행위 1건당 응답 1건이 구조적으로 보장)
- Telegram Bot API 레이트리밋 대응: 발송 큐 + 초당 발송 상한, 실패 시 재시도(백오프)

### 9.4 핵심 알림 outbox (v1.2)

인메모리 발송 큐만으로는 확정 알림이 큐에 있는 상태에서 프로세스가 죽으면 소리 없이 유실된다 — 핵심 신호에서의 조용한 실패(§11.1 1순위 리스크). 따라서:

- **D5 종국 알림**(`EXECUTION_CONFIRMED` — v1.11에서 `EXECUTION_INFERRED_ABOVE` 폐지로 단일)은 SQLite `alerts_outbox` 테이블에 **선기록 후** 발송 큐에 넣는다. Telegram 발송 확인 시 sent 마킹. D4 흡수 방어 알림(v1.11)은 outbox **미적용** — 관측 등급 신호로 재시작 후 재전송 가치가 낮고(다음 진행 발화가 대체), epoch/재시작에 누적이 리셋되는 설계(§8 D4)와도 정합
- 재시작 시 미발송(unsent) 행을 재전송한다. §9.2의 멱등 키 `(intent_id, terminal_state)`가 중복 발송을 차단하므로 재전송은 안전하다. 메시지에는 원 이벤트 시각을 표기한다 (지연 발송임을 수신자가 알 수 있게)
- **적용 범위 한정**: D2·D5 진행률 알림은 시효성 신호라 재시작 후 재전송 가치가 없고(다음 경계/버스트가 대체), watchdog 알림은 프로세스 사망 시 외부 경량 워치독 소관이므로 — outbox는 D5 종국 알림 전용
- **W 최종 리포트 (v1.13)**: `alerts_outbox` 미적용이되 동등한 보장을 전용 테이블로 얻는다 — `watch_levels` 행(§12.2)에 무효화 확정을 마킹 후 발송, `on_sent` 확인 시 행 삭제. 발송 전 크래시 시 재시작 복원이 마킹된 행을 발견해 재발송한다 (감시 종료의 무통지 방지). 주기 리포트는 시효성 신호라 미보장 (D2·진행률과 동일 취급)
- 구현 시점: **M4** (D5와 함께). `walls` 테이블을 M1로 선행 도입한 것과 같은 패턴이며, 전체 영속화(M6, §12)와 별개

### 9.5 텔레그램 수신 명령 (v1.13)

W 주시 레벨(§8 W)의 등록/해소는 재시작 없이 이루어져야 한다 — 재시작은 epoch 종료(활성 인텐트 `INTERRUPTED`, trade_window·D4 스트릭 리셋)를 수반하므로, "지금 이 레벨이 심상치 않다"는 순간에 관측 비용을 치르게 하는 설계는 기능 목적과 정면충돌한다. 따라서 발송 전용이던 봇에 수신 루프를 추가한다:

- **수신 루프**: `getUpdates` 롱폴링을 발송 워커와 별개의 asyncio 태스크로 구동. 발송기와 동일한 부분 실패 격리(§11.1) — 수신 장애·Telegram API 오류가 파이프라인을 막지 않으며, 지수 백오프로 재시도한다
- **수신 대상 (v1.14)**: 업데이트의 `message` **및** `channel_post` — 채널 게시물은 Bot API에서 별도 타입으로 도착하므로 `message`만 읽으면 채널 운영 시 명령이 무기록 스킵된다 (실배포 검증 발견)
- **인증 (v1.14 복수화)**: 발신 `chat.id`가 `telegram.command_chat_ids` 목록에 있는 메시지만 처리한다. 불일치는 무시(구조화 로그만) — 봇은 공개적으로 발견 가능하므로 이 검사가 접근 통제다 (채널에선 게시 권한자만 글을 쓸 수 있어 이중 통제). **발송 대상(`telegram.chat_id`)과는 분리** — 알림·주시 리포트는 단일 발송 대상 유지, 명령 응답만 발신 chat으로 라우팅한다
- **offset 영속**: 처리한 `update_id`를 SQLite `kv` 테이블(§12.2)에 저장한다 — 미저장이면 재시작 시 이전 명령이 재실행된다 (등록/해소는 멱등이라 피해는 제한적이나, 응답 메시지 중복 발송 방지)
- **단일 소비자 (운영 주의)**: `getUpdates`는 봇당 1소비자 전제 — 로컬 테스트와 VPS 인스턴스를 동시에 띄우면 409 Conflict로 양쪽 수신이 오염된다. 실토큰 로컬 테스트 시 VPS 정지 필요 (M2 실토큰 검증 런과 동일 관례)
- **문법**: `/watch <price>` · `/watch <lo>-<hi>` · `/unwatch <등록 시 리터럴>` · `/watching`(현황). 성공/실패를 즉시 응답한다 (등록 확인 에코, 파싱 실패·미존재 unwatch는 오류 안내). 그 외 텍스트는 무시

- 모든 수치 파라미터 > 0
- 비율류(`exit_ratio`, `fill_attribution`, `absorption_min_pct`, `realize_pct`, `progress_step_pct`, `episode_exit_ratio`, `delta_directional_ratio`, `delta_balanced_ratio`): 0 < x ≤ 1 (v1.11 — `realize_pct_above` 삭제. 신규 D4 키는 `absorb_multiple` > 1, `absorb_progress_step` > 0, `absorb_min_events` ≥ 1)
- `wall_tracker.record_min_qty_btc < thresholds.size_threshold_btc` (2단 임계치 순서)
- `thresholds.delta_balanced_ratio < thresholds.delta_directional_ratio` (성격 라벨 경계 순서, v1.3)
- `thresholds.vol_multiplier > 1` (상대 임계의 의미 조건, v1.3)
- `watchdog.heartbeat_interval < watchdog.stale_seconds`
- `watch.confirm_timeframe` ∈ {"15m", "1h"}, `watch.confirm_closes`는 정수 ≥ 1, `watch.report_interval_seconds` ≥ 60 (v1.13 — Telegram 초당 상한·스팸 하한)
- `telegram.command_chat_ids`는 문자열 목록, 최소 1개 (v1.14 — 빈 목록은 수신 기능 자체를 무의미하게 만드는 오설정)
- `exchanges.*`: `record_min_qty_btc < size_threshold_btc` (2단 임계치 순서 — 바이낸스와 동일 원리), `band_pct` > 0, `symbol` 비어있지 않음 (v1.16). 거래소별 섹션은 엄격 스키마(`_build_section` 패턴) 동일 적용 — 미지 키 거부

## 11. 비기능 요구사항

### 11.1 신뢰성 (최우선)

- **자가복구**: systemd `Restart=always, RestartSec=5` (또는 Docker `restart: unless-stopped`)
- **워치독 (v1.2 — 스트림별 감시)**: depth·diff는 `stale_seconds`(30 — 둘 다 100ms 주기라 공용 임계), aggTrade는 `trade_stale_seconds`(60 — 체결 발생 시에만 push라 별도의 느슨한 임계) 동안 수신이 없으면 **해당 스트림명을 명시한** `FEED_STALE`을 Telegram으로 발송하고 epoch를 종료한다(§5.4). **(v1.7 구체화)** 프로세스 하트비트: service가 `heartbeat_interval` 주기로 하트비트 파일 mtime을 touch(이벤트 루프 생존 신호 — 피드 정지는 FEED_STALE 소관이라 파이프라인 헬스로 게이트하지 않음)하고, 별도 경량 워치독(`deploy/watchdog_check.py`, systemd timer 60s 주기·시스템 python3 stdlib 전용)이 mtime 나이 > 60s(상수, interval×6)면 `PROCESS_DOWN` 알림 후 `systemctl restart`로 자동 복구한다 — 메인 프로세스가 행 상태여도 감지·복구. 알림은 정지/해소 전이당 1회, `is-active` inactive(의도적 정지)는 스킵, 발송 실패는 재시작을 막지 않음
- **재연결**: 지수 백오프(1s→최대 60s), 판정 재개는 §5.4 epoch 규칙(세 스트림 구독 확인 + 첫 depth 스냅샷)을 따름
- **부분 실패 격리**: Telegram 발송 실패가 파이프라인을 막지 않도록 발송은 비동기 큐로 분리
- **시계 (v1.2 상세화)**: 두 시각을 용도별로 분리한다. spot partial depth(`@depth20`)에는 거래소 시각이 없으므로(M1 스파이크 실측) "판정에 거래소 시각만"은 성립 불가.
  - `exchange_time` (aggTrade `T`, diff `E` — depth20에는 **부재**): **단일 스트림 내** 시간창(D2 trade_window 만료)과 기록·알림 표기 전용 + **(v1.13)** W 봉 버킷 경계·무효화 마감 판정(§8 W — 거래소 시각의 첫 판정 용도이나 aggTrade 단일 스트림 내 연산이라 "크로스 스트림은 monotonic만" 원칙과 무충돌. W의 리포트 주기 스케줄은 monotonic)
  - `local_monotonic_receive_time` (모든 이벤트에 수신 시 스탬프): **크로스 스트림 시간 비교 전부**(D4 refill 근접성 = aggTrade↔depth 비교, D3 접촉 episode 경계, 등록→확정 소요시간) + 지속시간 타이머(`PERSIST_SECONDS`, 쿨다운 — 구 `INTENT_TTL`은 v1.5에서 폐지) + 워치독 staleness — 세 스트림에 공통으로 존재하는 유일한 시계이며, 단조 시계라 시스템 시계 점프에 면역
  - 이벤트 레코드에는 두 값을 모두 저장한다 (`exchange_time`은 있는 스트림만)

### 11.2 성능 (충분 조건만)

- 처리량: depth 10 msg/s + aggTrade 피크 수백 msg/s 수준 — 단일 asyncio 프로세스로 충분
- 알림 지연: 이벤트 발생 → Telegram 발송 요청까지 5초 이내면 충분 (속도 비최우선)

## 12. 영속화

- SQLite 단일 파일: `events`(디텍터 이벤트), `intents`(상태기계 이력), `walls`(벽 레지스트리 현재 상태, v1.1), `alerts_outbox`(핵심 알림 outbox, v1.2 — §9.4, M4 선행), `watch_levels`(W 주시 레벨 + 누적, v1.13 — §12.2), `kv`(소형 운영 키-값 — 텔레그램 `update_id` offset 등, v1.13 — §9.5), `trades_sample`(선택)
- 목적: 임계치 튜닝, 사후 분석, 오탐 리뷰 + **벽 레지스트리 복원(v1.1)**. 리플레이 백테스트는 v2
- 재시작 시 인메모리 상태는 복원하지 않는다 — 진행 중이던 intent는 유실됨을 수용 (단순성 우선). DB에는 `INTERRUPTED`로 마킹. **(v1.2)** 이 마킹은 재시작만이 아니라 모든 epoch 종료(§5.4 — 스트림 단절·staleness·diff U/u 갭)에 동일하게 적용한다

**멀티 거래소 스키마 확장 (v1.16 — §5.5)**: **단일 DB 유지 + `exchange` 컬럼** — 파일 분리 대안은 기각(§16). 목적(임계치 튜닝·사후 분석)의 크로스 거래소 질의가 일원화되어야 하기 때문. 마이그레이션 4건 (기존 행은 전부 `'binance'` 백필):

1. `walls`: PK `(side, price)` → `(exchange, side, price)` — 거래소 간 같은 가격 벽의 행 충돌 방지. SQLite는 PK 변경 ALTER 불가 → **테이블 재생성** (신규 생성 → 백필 복사 → rename). 복원(`load`)·동기화는 파이프라인별 자기 거래소 행만
2. `events`: `exchange TEXT` 컬럼 + 인덱스 확장 — 경량 `ALTER TABLE` (v1.8 `appeared_alerted_since` 선례 패턴)
3. `intents`: PK `(run_started_at, intent_id)` → `(exchange, run_started_at, intent_id)` — 파이프라인별 D5 인스턴스가 각자 intent_id를 0부터 세므로 같은 런의 두 거래소 0번 인텐트가 충돌한다. 테이블 재생성
4. `alerts_outbox`: `exchange` 컬럼 + UNIQUE 키에 포함 `(exchange, side, price, terminal_state, recorded_at)` — 방어적 멱등의 거래소 스코프 유지. 테이블 재생성

`watch_levels`·`kv`는 무변경 (W는 바이낸스 전용 — §5.5). §12.1의 벽 레지스트리 복원·unconfirmed·TTL 규칙은 거래소 스코프로 동일 적용된다 — 한 거래소의 청취 공백은 그 거래소 행만 unconfirmed 마킹.

### 12.1 벽 레지스트리 영속화 (v1.1 — "상태 미복원" 원칙의 예외 ①. v1.13까지 유일한 예외였음 — ②는 §12.2)

원거리 벽 시야는 diff 이벤트의 **청취 누적**으로만 얻어지므로, 재시작 때마다 초기화하면 재수렴에 수 분~수 일이 걸린다. 따라서 `walls` 테이블을 두고 레지스트리를 동기화·복원한다.

- **저장 필드**: `price, side, last_qty, peak_qty, first_seen_at, first_seen_above_threshold, last_seen_at, unconfirmed, unconfirmed_since, appeared_alerted_since` — `last_seen_at`은 판정 미사용, 관측·튜닝용 (§7 v1.2). `appeared_alerted_since`(v1.8)는 APPEARED 알림이 발송된 스트릭의 `first_seen_above_threshold` 값 — 알림 1회 규칙(§8 D1)의 멱등 키로, 재시작을 넘어 보존되어야 억제가 성립한다
- **staleness 처리**: 신뢰도 하락은 **청취 공백**(프로세스 다운타임, WS 재연결 갭)에서만 발생한다 — 연결이 살아있는 동안 이벤트가 없다는 것은 "변화 없음"을 뜻하므로 값은 유효하다. 규칙:
  1. 청취 공백 발생 시(재시작 복원 직후, **diff 스트림**의 단절·staleness·U/u 갭 직후 — §5.4. aggTrade/depth만의 공백은 해당 없음) 레지스트리 전체를 `unconfirmed`로 마킹하고 `unconfirmed_since`를 기록한다 (이미 unconfirmed인 항목의 `unconfirmed_since`는 갱신하지 않음 — 최초 마킹 시각 유지)
  2. `unconfirmed` 레벨은 D1 APPEARED 신규 발화를 억제하되, `first_seen_above_threshold`를 보존한다 — 스푸핑 지속시간 필터 타이머(§8 D1)를 리셋하지 않기 위함 (v1.2 정정: 구판은 이 타이머의 기준 필드를 `first_seen_at`으로 오기했음. `first_seen_at`도 관측 데이터로 함께 보존한다)
  3. 해당 가격에 diff 이벤트가 1건이라도 도착하면(값 불문 — 절대 잔량이 오므로) 그 레벨의 `unconfirmed`를 해제하고(`unconfirmed_since` 삭제) 값을 덮어쓴다. 특정 가격만 조회하는 능동 API는 없으므로(REST는 원거리에 닿지 않음) 수동적 재확인이 유일한 방법이다
- **TTL 청소 (v1.2 개정 — `unconfirmed` 전용)**: `unconfirmed_since`로부터 `wall_tracker.ttl_days`(기본 7일, 설정값) 동안 재확인 이벤트가 없는 unconfirmed 레벨은 레지스트리에서 삭제한다. **확인된(confirmed) 벽은 나이를 이유로 삭제하지 않는다** — 연결이 살아있는 동안의 무이벤트는 "변화 없음 = 유효"이므로(위 staleness 원칙), 구 규칙(`last_seen_at` 기준 전체 적용)은 14일간 조용히 서 있는 진짜 원거리 벽을 삭제해 이 원칙과 모순되고, 삭제된 벽은 다음 변경 이벤트까지 재관측이 불가능해 §14의 사각지대를 재생산했다. v1.2 이후 살아있는 연결에서의 소멸은 tombstone/하한 미만 이벤트로 즉시 정리되므로(§8 D1), TTL이 청소할 대상은 "청취 공백 중 소멸해 tombstone을 못 받은 항목"뿐이고 이는 정확히 unconfirmed 집합이다. 기산점이 `last_seen_at`이면 공백 직전 13일 무변경이던 정상 벽이 공백 하루 만에 삭제되므로 `unconfirmed_since` 기준으로 한다. 트레이드오프: 실존하지만 공백 후 7일간 무변경이라 재확인받지 못한 벽의 유실 가능성을 수용한다 (무한 보존 시 쓰레기 무한 누적). `events` 이력 로그는 삭제하지 않는다 (M6 튜닝 데이터 보존)

### 12.2 주시 레벨 영속화 (v1.13 — "상태 미복원" 원칙의 예외 ②)

주시 목록은 사용자가 명령으로 공급한 **입력**이지 파생 상태가 아니다 — 크래시/재시작에 증발하면 사용자가 인지하지 못한 채 관측이 끊긴다(조용한 실패). 누적 카운터도 복원한다(사용자 확정 2026-07-23): 주시는 수십 시간 지속되는데(64.9k 40h 사례) 재시작마다 0이 되면 장기 흡수 관측이라는 기능 목적이 반감되고, flush 비용은 리포트 주기당 UPDATE 1건으로 무시 가능하다.

- **`watch_levels` 테이블**: 구역(lo, hi)·등록 리터럴(unwatch 매칭·표시용)·등록 시각·역할·회차 수·첫 접촉 시각·누적 taker 매도/매수·excursion 극값·이탈 마감 연속 카운트·무효화 마킹(최종 리포트 발송 보장용, §9.4)
- **flush 시점**: 등록/해소는 즉시, 그 외 주기 리포트 발송 시 + 회차 종료 시 + 무효화 확정 시
- **복원 규칙**: 재시작 시 전체 복원. 진행 중이던 회차는 공백으로 단절 처리(재진입 시 새 회차), 이탈 마감 연속 카운트는 리셋(§5.4의 공백 낀 봉 판정 제외와 동일 원리), 다음 리포트에 관측 공백 플래그를 표기한다. 무효화 마킹된 채 미발송인 행은 최종 리포트 재발송 후 삭제(§9.4)
- **`kv` 테이블**: 텔레그램 `update_id` offset(§9.5) 등 소형 운영 키-값

각 단계는 독립 배포 가능. M2 시점부터 실사용 가치 발생. Kraken·Bitfinex 어댑터는 M8 완료(공통 기반 + Coinbase 실증) 후 후속 마일스톤으로 — 한계비용은 어댑터 한 벌 + 픽스처 캡처 + 임계 분포 수집 (§5.5).

**결정적 replay 테스트 (v1.2)**: 합성 + 실캡처 이벤트 시퀀스를 재생하는 테스트 픽스처로, 정상 경로만이 아니라 **재연결(epoch 종료/재개), 스트림 순서 역전, 이벤트 누락(diff U/u 갭 포함)** 케이스를 반드시 포함한다. 실전 알림 각 1건(M4) 같은 소표본 확인은 경계 경로를 커버하지 못하므로, 이것이 M3/M4 정확성 검증의 주 수단이다 (v1.4 — M3의 Bookmap 육안 대조는 기각되어 replay 테스트가 유일한 완료 기준, §15 #5). §12의 "리플레이 백테스트(v2)"와는 다른 것 — 이것은 임계치 튜닝용 재생이 아니라 판정 로직의 결정성 검증용 테스트다.

**오탐 지표 (v1.2, M6에서 확정)**: 초기 목표값 — D5 종국 알림 오탐(사후 리뷰로 판정) **주 1건 이하, 목표 0**; D1/D2 알림 **시간당 평균 3건 이하** (스팸 상한). M6 튜닝 루프에서 실데이터로 재조정하며, 이 지표 달성이 M6 완료 기준의 일부다.

## 16. 참고 — 기각된 대안

- **경로 A (Bookmap 인더루프)**: Bookmap L1 Python API 애드온으로 구현. Absorption/Sweeps 독자 지표를 그대로 소비할 수 있으나, GUI 앱 24/7 상주(Windows/GPU VPS, RDP, 크래시 관리)라는 운영 부담과 Global+ 구독 비용 발생. 신뢰성 우선 원칙에서 헤드리스 서비스 대비 열위 → 기각. 단, Bookmap 독자 시그널이 필수로 판명되면 재검토
- **Bookmap 데이터 export 활용**: 메뉴 export는 체결(Time & Sales)만 CSV 지원, 오더북은 불가(.bmf는 암호화 바이너리). 실시간성도 없음 → 기각
- **diff depth 스트림으로 전체 북 유지**: 정밀하나 시퀀스 재조정 복잡도와 드리프트 리스크 → 기각 유지. (v1.1 주의) §5.1의 "이벤트 탭" 방식은 full book을 유지하지 않으므로 이 기각 사유(시퀀스 일관성 관리)와 무관하다 — 혼동 금지
- **외부 데이터 API(Coinglass 등) 구독**: 원거리 벽 데이터를 유료 API로 조달하는 대안. 외부 의존·비용·지연이 생기고, 동일 원천(공개 diff 스트림)을 자체 수집 가능함이 실측 확인되어 기각 (v1.1)
- **W 무효화의 ATR 기반 버퍼 (v1.13)**: 통상 관행(마감가 버퍼 0.5~1.0×ATR)이나 지표 창고(14봉 워밍업)가 필요하고 그 상태가 재시작마다 리셋되는 §12 원칙과 부정합 — 고정 %(`invalidate_buffer_pct`) + config 조정으로 대체
- **kline 스트림 구독 — W 봉 조립용 (v1.13)**: 4번째 스트림은 §5.1 3-스트림 역할 분리와 스트림 헬스 모델(§5.4)의 확장 비용 대비 이점 없음 — aggTrade `T` 버킷 자체 조립로 대체 (마감가 = 마지막 체결가로 동일)
- **W 돌파/이탈 확정 후 역할 반전 유지 (v1.13)**: S/R 플립은 실재하나(65.6k 07-21 돌파 → 07-22 지지) 재등록이 명령 1개인 반면, 넓은 레인지 내 단일가 주시에서 반전 유지는 핑퐁 소음 위험 — 종료로 확정, 필요 시 재검토
- **W 주시 개수 상한 (v1.13)**: 구체적 실패 시나리오로 역추적되지 않아 미도입 — 등록이 수동(명령 1건당 1개)이라 자연 바운드되고, 발송 스팸은 활동 게이팅이 억제
- **거래소별 DB 파일 분리 (v1.16)**: walls·intents PK 재생성 마이그레이션을 피할 수 있으나, 영속화의 존재 목적(임계치 튜닝·사후 분석 — §12)인 크로스 거래소 질의가 ATTACH 다중 파일로 분산됨 — 단일 DB + `exchange` 컬럼으로 확정. 단일 프로세스 asyncio라 쓰기 경합도 비쟁점
- **신규 거래소 근접북 로컬 풀북 유지 (v1.16)**: 바이낸스 `@depth20@100ms` 등가물이 없어 검토된 대안이나, D2·D4 제외 스코프에서는 소비처가 없다 — §5.1 결정 1이 회피한 드리프트 버그 클래스를 무근거로 재도입하는 것이라 기각. D3의 best price는 ticker 합성 top-1 스냅샷으로 충분 (§5.5). D2·D4를 신규 거래소로 확장하는 날 재검토
